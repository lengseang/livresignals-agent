# T0.3 · Design: stop duplicate real buys after a crash (F1)

Status: **design only, waiting on the owner.** `trend_follower.py` places real orders, so
implementing this is T8.1 and needs the owner's approval (LOOP.md §2).

## Problem

`scripts/trend_follower.py` (cron every 4h, `TREND_REAL=1`, real Binance spot).

There are two ways the real book can forget a buy it already made. Either one makes the next run buy again.

**A. Crash between the order and the save.** The buy happens at `:301`
(`ex.create_order(s, "market", "buy", qty)`). It is appended to `real["open"]` in memory at
`:302`, but written to disk only by `save(st)` at `:310`, after the whole buy loop. If the
process is killed in between (OOM, host reboot, a manual kill), the coins are in the wallet but
`trend-state.json` does not list them. Four hours later the same symbol is still a candidate,
so it is bought again. (Exceptions are not a path here: the buy loop catches them at `:307`.)

**B. A corrupt state file is read as empty.** `save()` (`:107`) calls `write_text()` in place,
which is not atomic. If the process is killed mid-write, the file is truncated. `load()` (`:98`) then
hits a JSON error, **silently** returns a fresh empty state (`real.open = []`), and the next
run buys up to `MAX_POS` new positions on top of the ones it no longer knows about.
The earlier positions are orphaned: nothing will ever sell them.

**C. Two runs at once.** The script is started by cron every 4h (`config/crontab.backup:41`)
with no lock. If one run hangs (the exchange calls have no overall deadline) and is still
alive when the next starts, both read the same state and both can buy the same symbol.

All three paths break the owner's "one risk that matters" rule.

## Facts this design relies on (checked 2026-09-25)

- Binance `POST /api/v3/order`, `newClientOrderId`: *"A unique id among open orders…
  Orders with the same `newClientOrderID` can be accepted only when the previous one is
  filled."* A market order fills immediately, so **reusing a client ID does not block
  a duplicate market buy.** It is useful as a lookup key, not as a lock.
  Source: [binance-spot-api-docs rest-api.md](https://github.com/binance/binance-spot-api-docs/blob/master/rest-api.md) (line 2153 of the fetched copy).
- `GET /api/v3/order` accepts `origClientOrderId`, so an order can be found by the ID we chose.
  Same source, "Query order (USER_DATA)".
- ccxt 4.5.73 (the version pinned in `requirements.txt`): `create_order(..., params={"clientOrderId": X})`
  sends `newClientOrderId=X` unchanged for spot (`ccxt/binance.py`, `create_order_request`:
  read at `:6795`, mapped at `:6884`/`:6898`); with no ID given, ccxt generates `brokerId + uuid22`.
  `fetch_order(id=None, symbol, params={"clientOrderId": X})` sends `origClientOrderId=X`
  (`fetch_order` at `:7149`, mapped at `:7205`).
- `check-books.py` reads `real.open` and ignores unknown keys (`:244-262`), so a new
  `real.pending` key does not break the guard.

## Options

1. **Save right after each order.** This narrows window A but doesn't close it
   (a crash between `create_order` returning and the save still loses the buy), and it does nothing for B.
2. **Reconcile from the wallet only.** At the start of each run, treat any REAL_SYMS coin
   with a non-dust wallet balance as held. This catches A and B, but it can't tell our buy from
   coins that were already there (DOGE dust, manual buys). It also has no entry price, and we
   must not invent one (owner rule 2).
3. **Write-ahead intent + client order ID + atomic state + run lock (chosen).** Record the intent to
   buy, durably, *before* sending the order, under an ID we choose. On the next run,
   resolve any unresolved intent by asking Binance about that exact ID. Make saves atomic, and make a
   corrupt file stop the run instead of resetting it.

## Chosen design

### 1. Atomic save
`save()` writes to `trend-state.json.tmp`, flushes and `fsync`s, then `os.replace()` swaps it
over the real file, which is atomic on POSIX. The file is then always either the old
version or the new one, never half-written.

### 2. A corrupt state fails closed
`load()` keeps returning the default state when the file **does not exist** (first run).
If the file exists but is unreadable, it raises `StateCorrupt`. `main()` then does not trade:
it prints an error, sends one alert through the existing `notify()` path, and exits non-zero.
A person has to look. An empty book must never be the automatic outcome of a read error.

### 2b. One run at a time
At the start of `main()`, take an exclusive non-blocking `fcntl.flock` on
`data/trend-follower.lock` (POSIX; the VPS is Linux). If the lock is held, print
"previous run still active", send one alert and exit without trading. The OS
releases the lock when the process dies, so a crash can't leave a stale lock behind.

### 3. Write-ahead intent
For each real buy:

```
cid = f"tf-{symbol_base}-{utc_yyyymmddHHMM}-{short_uuid}"   # ≤ 36 chars, [A-Za-z0-9-_]
real["pending"].append({"cid": cid, "symbol": s, "qty": qty, "ts": now, "state": "sent"})
save(st)                                   # durable BEFORE the order
od = ex.create_order(s, "market", "buy", qty, params={"clientOrderId": cid})
move the pending entry to real["open"] using the FILLED values from `od`
save(st)                                   # durable right after the fill
```

The `open` record takes `qty` and `entry` from the exchange's fill (`od["filled"]` and
`od["average"]`), **not** the planned `qty` and candle `px`. If the response lacks them,
the record is written with `"entry": null, "entry_status": "UNKNOWN"`, and the
notification says so. No number is invented.

### 4. Resolve pending intents at the start of every run
Before any exit or entry logic, for each item in `real["pending"]`:

| Binance answer for `origClientOrderId=cid` | Action |
|---|---|
| found, `status=FILLED` | move to `real.open` with the fill's qty and average price |
| found, `PARTIALLY_FILLED` / `NEW` | leave it pending; **block new buys this run**; alert |
| found, `CANCELED` / `REJECTED` / `EXPIRED` with no fill | drop the intent and log it |
| not found (`OrderNotFound`) and the intent is < 24h old | the order never reached Binance: drop it and log it |
| any other error (network, auth) | **block all new buys this run**, keep the intent, alert |

While any intent is unresolved, the run may still manage exits but must not open anything
new. That is the whole point: if we don't know whether we already bought, the answer is to not buy.

### 5. A belt-and-braces cap from the wallet
Before buying, count REAL_SYMS coins whose wallet value is at or above a dust threshold
(proposed $1; **the owner should confirm**, because the real dust level of this account isn't in the repo). If that count plus the new
buy would exceed `MAX_POS`, skip. This is a guard, not a record. It never writes to `real.open`.

## Pre-mortem: it's 3 months later and this failed. Why?

- **The intent was saved but the process died before `create_order` was sent.** Handled:
  the ID isn't found, so the intent is dropped. **Open question:** the Query order section
  does not say how long an order stays queryable. So "not found" is trusted only for
  intents younger than 24h (a run fires every 4h, so a fresh intent is always resolved well
  inside that). An older unresolved intent is never dropped automatically: it blocks buys and alerts.
- **Clock skew makes the ID collide.** The `short_uuid` suffix makes collisions practically
  impossible.
- **`fsync` or `os.replace` behaves differently on the VPS filesystem.** The filesystem
  type is not known from the repo. The implementation PR must include a kill-mid-write
  test, and the owner should confirm the mount type (`df -T /opt/trading-agent`).
- **Someone "fixes" the fail-closed error by deleting the state file.** Then the bot
  starts from empty and can double-buy. Mitigation: the alert text says exactly
  what *not* to do, and the wallet cap (§5) still limits exposure to `MAX_POS`.
- **A dependent reader breaks.** `fee_audit.py:99` and `check-books.py` read this
  file. Only a key is added (`real.pending`); nothing is renamed. The implementation PR must run
  `check-books.py` against a fixture state file.

## Test plan (for the implementation PR, T8.1)

All tests run against a fake exchange object; no network (the `tests/loop` guards enforce this).

1. Crash after the intent is saved and before the order: the next run finds no order, drops the intent, and buys at most once.
2. Crash after the order and before the second save: the next run finds FILLED, moves it to `open`, and doesn't buy that symbol again.
3. Truncated state file: `load()` raises, `main()` places no order, exits non-zero and alerts once.
4. Exchange error while resolving: no new buys that run, the intent is kept.
5. Fill without an average price: `entry` is `null` with `entry_status: UNKNOWN`, and the notification says so.
6. Atomic save: the file is always valid JSON after a kill at any point (simulated with a failing `os.replace`).
7. Lock held: a second `main()` while the lock is held places no order and exits.
8. `check-books.py` still passes on a state file that contains `real.pending`.

## Scope and what is not included

- One file changes (`scripts/trend_follower.py`) plus a new test file. There is no change to the exit path;
  F2 and F3 are separate designs (T0.4 and T0.5) and separate PRs.
- No crontab, `.env` or ledger changes.
- Rollout: deploy between two 4h runs, while no intent is in flight; the first run after deploy
  has an empty `pending` list.
