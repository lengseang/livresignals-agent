# T0.13 · Design: real position drift — does the trend ledger match the exchange?

Status: **built, in review.** Branch `loop/T0.13-real-position-drift`, stacked on
the T0.12 tip.

## The finding that created this task

On 2026-10-09 the trend book (`trend_follower.py`, REAL money, `TREND_REAL=1`)
logged `real positions: 3/3 | REAL=ON` at every 4-hour run. Three real slots
were full, so the book would not size a new signal.

It was not full. `trend-state.json -> real.open` claimed three positions:

    ARB/USDT   qty=34.8   entry=0.1445
    NEAR/USDT  qty=2.3    entry=2.369
    LINK/USDT  qty=0.43   entry=12.582

The exchange held **none** of them. Non-zero balances were dust (ADA/BNB/SUI/XRP)
plus ~$20 free USDT. LINK had been sold by hand at 12.885 on 2026-10-08 (the
commit `07262d2` records the manual sale; the ledger never learned). ARB and NEAR
were gone well before that.

Consequence: the real book believed all three slots were consumed and stood idle.
Any signal it wanted to take could not be sized. This is real money not working,
invisible to every existing report — because every report reads our own files,
and our own files were the thing that was wrong.

## Why a reader, not a fix to the writer

`trend_follower.py` is on the LOOP.md §2 never-edit list (real-money script, no
touch). So this task adds a **read-only monitor**, exactly the discipline T0.5/T0.6
established: detect drift, say so loudly, never silently repair. Repairing a
real-money ledger is a writer change, owner-gated (T8.1).

## Design

`scripts/real_position_drift.py`:

- reads `data/trend-state.json -> real.open` (the claim). A corrupt or missing
  file **raises** — reading it as "no positions" would report a clean account and
  hide the very drift this exists to find.
- reads exchange balances (the fact) through `live_balances()`, which is only
  called from `main()`. The pure core (`classify`, `reconcile`, `render`) takes a
  plain `{ASSET: qty}` dict, so tests run on fixtures with no socket and no
  real-money import (the `tests/loop` guards enforce both).
- classifies each claim MATCH / PARTIAL / MISSING / EXCESS / UNKNOWN, worst first.
- exits **1 when drift exists**, 0 when clean — so a cron alert and the heartbeat
  can act on it.

## The one judgement call, and why it matters

`held=None` means **the balance read failed** → UNKNOWN, never a phantom zero
(owner rule 2). But an asset **absent from a successful read** is a real zero:
Binance omits zero balances. That must be MISSING, not UNKNOWN.

Collapsing the two would make the monitor blind to the exact bug it exists to
find — the 2026-10-09 positions are absent from the balance map, so an
UNKNOWN-on-absence rule would print "3 UNKNOWN" and never cry drift. A first cut
of `reconcile()` did exactly that; the test written from the real state caught it
(`test_reconcile_reproduces_the_live_2026_10_09_drift`). The caller now states
which case it is via `balances_known`.

## Adversarial self-review ("it is 3 months later and this failed: why?")

1. **The monitor is written but nothing runs it.** A tool nobody schedules is a
   tool that does nothing. Mitigation: this is a read-only script, so scheduling
   it is a safe crontab line — but the crontab is on the owner's no-touch list,
   so that is an escalation, not a loop action (see below).
2. **It fights the writer.** `trend_follower` keeps re-deriving its 3/3 from the
   same stale `real.open`, so the monitor will keep reporting MISSING until the
   state is reconciled. That is correct — a monitor should stay red until reality
   and the ledger agree. The loop must not silence it by zeroing the ledger.
3. **A dust false-positive.** A position sold down to dust (e.g. 0.0001 left)
   reads PARTIAL, not MATCH. Accepted: PARTIAL is worth a human look, and the
   alternative (tolerating small drift) is how the 58→23 DOGE shape hid.
4. **Symbol format again.** `regime_trader` stores `NEARUSDT`; trend stores
   `NEAR/USDT`. `_base()` takes the part before `/`, and a bare venue symbol is
   left verbatim (it has no slash and must not be guessed apart — the T0.12
   rule). trend's own book always uses the slash form, so this is exact for
   `real.open`.
5. **The exchange read is slow / rate-limited.** One `fetch_balance`, no per-symbol
   calls. If it fails, every held value is UNKNOWN and the run still exits 1
   (unverified ≠ clean).

## Test plan (shipped)

`tests/loop/test_real_position_drift.py`, 19 tests, no network, no real-money
import:
- classify: MATCH (exact + within tolerance), MISSING (0 and absent), PARTIAL
  (the 58→23 shape), EXCESS, UNKNOWN (read failed), ledger-zero-but-held.
- reconcile: reproduces the live 2026-10-09 three-MISSING state; worst-first
  ordering; empty book is clean; `_base` keeps a bare venue symbol verbatim.
- load: nested `real.open` read; corrupt file raises; missing file raises.
- main: exit 1 on drift, exit 0 on match, exit 1 when the exchange read fails
  (UNKNOWN is still a failure, not a silent pass).

Evidence: `pytest tests/loop` → **393 passed, 3 skipped** (baseline 374 + 19).
`compileall` clean. Live read-only run against the real exchange prints all three
positions MISSING and exits 1.

## Discovered / escalated

- **Escalation E8 (new):** schedule `real_position_drift.py` (crontab is the
  owner's) and reconcile `trend-state.json real.open` — the three phantom
  positions are live right now and are costing real trading slots. The loop can
  build the detector but must not rewrite the real-money ledger.
- **Related, not fixed here:** the one `real.closed` record (DOGE) has
  `pnl_usd: null` despite `pnl_gross_usd: 0.0851` — a computable net left as
  UNKNOWN. Same T0.5 "record every real exit honestly" family; the writer
  (`trend_follower.py`) owns it and is owner-gated.
