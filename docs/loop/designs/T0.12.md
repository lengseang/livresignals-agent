# T0.12 — does a non-zero exit reach the owner on every `--quiet` cron job?

Status: design + shipped audit tooling. **Wrapper edits are owner-gated** (see §5).

## 1. Problem

`lesson-loop-main-crashed-2026-10-19.md` recorded one instance: the lesson wrapper
ended with `exit 0`, so a crash on every run reported `last_status: ok` for 24
hours. That wrapper was fixed (commit `2ac046e` lineage). Its closing note said
the **other** quiet jobs were never audited. This is that audit.

The shape to look for is not "does the script handle errors". It is:

> A job that is silent on success will also be silent on failure **unless
> something explicitly makes failure loud.** Two things can do that: (a) a
> non-zero exit code, (b) a printed line. A wrapper that forces `exit 0` removes
> (a); a job that redirects its own stdout removes (b). Either alone is enough
> to swallow the failure.

## 2. What the scheduler actually does (measured, not assumed)

From `~/hermes-home/cron/executions.db` and `hermes cron runs`:

- A non-zero exit is recorded as `status=failed` with the text
  `Script exited with code N` **plus the captured stdout**, and it is delivered.
  Verified on live data: `d071de6fa4a4` (v2-top8-gate-watchdog) failed twice,
  2026-11-05T09:00 and 21:00, and the full `V2 GATE FAILURE` text is in the
  attempt record.
- A zero exit with empty stdout is recorded as `completed`. Nothing is
  delivered — which is the intended quiet-on-no-op contract.
- `hermes cron runs <job>` prints the attempt's stdout, so a past failure is
  recoverable after the Telegram message has scrolled away.

Consequence: **`exit 0` on a crashed job converts it into a `completed` run with
no delivery.** The job simply disappears — it looks exactly like a healthy
no-op. This is the 2026-10-19 shape, and it is detectable only from the exit
code.

## 3. Audit result — 20 scheduled jobs, 9 quiet-with-suppressed-output

Method: read every wrapper in `~/hermes-home/scripts/`, then classify the
exit-code path. `.orig` scripts were read, not executed (they write prod logs).

| job | wrapper exit path | verdict |
|---|---|---|
| trade-lesson-loop | propagates `$RC`, prints ⚠️ | **fixed** (2026-10-19) |
| strategy-lab-15m | `.orig` → `exit $rc`; `exit 0` on success | ok |
| strategy-book-daily | `strategy_book.py` rc checked; **`strategy_compact.py` rc NOT checked** | **defect B** |
| scrape-history-daily | rc checked | ok |
| news-scrape-4h | rc checked | ok |
| ensemble-paper-5m | rc checked | ok |

| **trading-digest (1/day)** | **`exit 0` hardcoded, rc discarded** | **defect A** |
| hunt-strategy-search | `exit 0` but prints survivors; silent "nothing" is by design | ok (documented) |

| remaining 8 | agent-prompt jobs, not scripts | n/a |

### Defect A — `run_scan_ping.sh`, `run_trading_digest.sh`

Both are the pre-2026-10-19 template verbatim:

```bash
OUT="$(... scan_ping.py 2>&1)"
if [ -n "$OUT" ]; then printf '[%s] %s\n' SCAN "$OUT"; fi
exit 0          # <-- rc never captured
```

Reproduced in `/tmp/t012`: a script that raises prints the traceback, the
wrapper echoes `[SCAN] Traceback...`, and the wrapper exits **0**. Cron records
`completed`. **The traceback is delivered as if it were a normal scan line** —
so the failure both looks like an ordinary message *and* is marked successful.

Severity: `scan_ping.py` is the STALL ALERT monitor (48×/day). If it dies, the
monitor that is supposed to notice a dead bot is itself dead, silently. The
`--quiet` success path is the only reason this has not bitten yet: the script
has run 88 times without raising.

Wording is deliberately **not** changed — that is the owner-facing decision
named in the task. Only the plumbing (keep the rc) is shipped.

### Defect B — `run_strategy_book.sh`

`timeout 2400 strategy_book.py` has its rc checked; the next line,
`timeout 600 strategy_compact.py`, has none. A compaction failure (up to 10
minutes) leaves `$_?` non-zero but the script continues and ends `exit 0`.
The ensemble file it writes feeds the paper ensembles, so a silent compaction
failure means the book stops being refreshed while the job reports success.

## 4. Failure modes of this design

- **False alarm from a benign non-zero rc.** Some scripts exit 1 on "nothing to
  do". Checked: none of the audited scripts do; all return 0 on empty. The
  known-intentional silence is `hunt`, which is left alone.
- **Double-reporting.** If a script already prints its own error *and* exits
  non-zero, the owner gets the text plus the scheduler's `exited with code N`
  line. Acceptable: the rc line is the machine-checkable half.
- **Locking in the message wording before the owner decides.** Mitigated: the
  shipped tool reports whether the rc is propagated, and never asserts a
  message body.

## 5. Adversarial self-review — "it is 3 months later and this failed: why?"

1. *Someone re-templates from the old `exit 0` block.* This is exactly how A
   and B arose. So the check is a **test**, not a doc: `tests/loop/test_quiet_cron_exit.py`
   fails if any wrapper in the audited set discards the rc.
2. *A new job is added and nobody adds it to the list.* The test enumerates the
   wrappers found in the scripts dir, so a new `run_*.sh` with `exit 0` after a
   captured `$OUT` fails the test without being listed.
3. *The test shells out to bash and is brittle.* It uses `bash -n` for syntax
   and a static scan for the `exit 0`-after-capture shape, with one behavioural
   test on a throwaway crash script. No prod script is executed.
4. *Owner declines the wrapper edit.* The audit and test still ship; the two
   defects stay red and are named in ESCALATIONS so they cannot be forgotten.

## 6. Test plan

`tests/loop/test_quiet_cron_exit.py`:
1. every audited wrapper parses (`bash -n`);
2. no wrapper that captures `$OUT` then hardcodes `exit 0` **without** also
   propagating `$RC` (catches A and B's class);
3. behavioural: a wrapper built from the fixed template returns non-zero when
   the inner script crashes, and zero when it is silent;
4. the fixed template is silent with empty stdout (no-op stays quiet).
