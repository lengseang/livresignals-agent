# T0.4 · Design: a failed real sell must not strand the position (F2)

Status: **design only, waiting on the owner.** The change touches order code in
`scripts/trend_follower.py`, so implementing it is T8.1 and needs approval (LOOP.md §2).
It builds on T0.3 (atomic save, run lock) and is a separate PR.

## Problem

The exit branch (`trend_follower.py:232-274`) runs only when the **paper** flag says held:
`held = pos.get(s, {}).get("long", False)` (`:221`). Inside that branch, the paper flag is flipped to
not-held (`:239`) **before** the real sell is attempted (`:271`). If the sell raises, the
`except` at `:273` records an `ERR` event and moves on. The state is then saved (`:310`) with:

- `positions[s].long = False`: paper says flat
- `real.open` still containing `s`: the coins are still in the wallet

From the next run on:

1. **The exit is never retried.** The exit branch requires `held`, which is now False.
2. **The hard stop is off.** `hard_hit` (`:224`) also requires `held`, so a real position can
   fall past −15% with nothing watching it.
3. **The same coin can be bought again.** When `want` turns true, the symbol becomes a
   candidate (`:226-231`). The buy loop (`:284-308`) checks `len(real["open"]) >= MAX_POS`
   but never checks whether `s` is already in `real.open`.
4. The stranded record still counts toward `MAX_POS`, so capacity shrinks silently.

Severity: **High.** It's live, it's real money, and it leaves a position with no stop.

## Facts relied on (checked against installed ccxt 4.5.73)

- These exception classes exist: `InsufficientFunds` (direct parent `ExchangeError`),
  `InvalidOrder`, `NetworkError` (direct parent `OperationFailed`), `RateLimitExceeded`, `OrderNotFound`.
- Binance's "Account has insufficient balance for requested action." maps to
  `InsufficientFunds` (`ccxt/binance.py:2791`); code `-2010` (NEW_ORDER_REJECTED) maps to
  `InvalidOrder` (`:2523`).

## Chosen design

### 1. Manage real positions from `real.open`, not from the paper flag
After the paper loop, add a separate **real exit pass** that iterates over `real["open"]`.
For each real position it fetches that symbol's closes (reusing the data already fetched this
run where possible) and exits when **either** of these holds:
- `not coin_trend(closes)`: the same trend-break rule as paper
- `px / rp["entry"] - 1 <= -HARD_STOP`: the hard stop, measured from the **real** entry. If the
  real entry is `null` / `UNKNOWN` (see T0.3), the hard stop is measured from the paper entry and
  the record says `stop_basis: "paper"`, so no number is presented as something it isn't.

The paper exit block stops touching real money at all. It only updates the paper book. The
paper and real books then can't desynchronise each other.

### 2. A failed sell stays open and is retried
On a sell failure the record stays in `real.open` and gains:
```
"exit_pending": {"since": <iso>, "attempts": n, "last_error": "<class>: <msg[:80]>"}
```
The next run sees `exit_pending` and tries again, even if the trend has since recovered,
because the decision to exit was already made.

**Every sell uses the T0.3 write-ahead mechanism too:** a `clientOrderId` is saved in
`exit_pending.cid` *before* the sell is sent. Before any retry, the run first queries that
`cid` (`fetch_order` with `clientOrderId`). If it was FILLED, the exit is recorded from that
fill and nothing is re-sent. A retry never runs "blind", so a sell that timed out on our side
but executed on Binance is never sent a second time. That matters because the wallet may hold
other units of the same coin (dust, manual buys) that a blind retry would sell.

Handling by exception:

| Exception | Meaning | Action |
|---|---|---|
| `NetworkError`, `RateLimitExceeded` | transient | keep `exit_pending`, retry next run |
| `InsufficientFunds` | the wallet holds less than we asked to sell | re-read the wallet balance; sell `min(booked, free)` if ≥ the market minimum, otherwise go to F3 handling (T0.5) |
| `InvalidOrder` (includes −2010, below min notional) | the amount can't be sold | stop retrying; mark `exit_blocked` and alert; F3 decides how it's recorded (T0.5) |
| anything else | unknown | keep `exit_pending`; alert on the **first** failure and again once `attempts` reaches 3 |

Alerting uses the existing `notify()` path; there's no new channel.

### 3. Never hold the same symbol twice
In the buy loop, skip `s` if any entry in `real.open` (or `real.pending`, from T0.3) has
`symbol == s`. One line, and it closes failure 3 above for every cause, not just this one.

### 4. Recording the exit
A successful real sell appends to the log with the **fill** price (`od["average"]`) and the
filled amount, marked `"book": "real"`. If the fill price is missing from the response, the exit price is
`null` with `exit_status: "UNKNOWN"` (owner rule 2). The paper log entry at `:236` stays as the paper
record. This overlaps with F3 (T0.5), which owns the rules for dropped and unknown exits;
this design only guarantees the sell is retried and the position stays tracked.

## Pre-mortem: it's 3 months later and this failed. Why?

- **An exit that is retried forever while the coin keeps falling.** `exit_pending` survives trend
  recoveries on purpose. The retry is a market sell, so the only way it keeps failing is an
  exchange-side block, which is alerted at attempts 1 and 3. A human decides.
- **A double sell.** The sell times out client-side but executed on Binance. The first draft
  assumed the retry would simply fail with `InsufficientFunds`. That's wrong whenever the wallet
  holds other units of the coin, which it did in the DOGE incident. Fixed by the sell-side
  `cid` lookup in §2: a retry is only sent after the previous `cid` is confirmed not filled.
- **The `cid` lookup itself fails (network).** Then no retry is sent that run; the position stays
  `exit_pending` and is tried again next run. Failing to sell for 4h is recoverable; selling twice
  may not be.
- **The real exit pass uses stale closes.** It reuses closes fetched in the same run
  (within seconds), the same freshness the paper loop uses today.
- **Behaviour change surprise.** Today a real exit happens only when paper also exits. After
  this change they can disagree, for example after a crash where paper and real diverged. That's the point, and the
  PR notes will say so explicitly.

## Test plan (for T8.1)

Fake exchange object, no network (`tests/loop` guards).

1. Sell raises `NetworkError`: the record stays in `real.open` with `exit_pending.attempts == 1`; the next run retries and succeeds.
2. Paper flat but real still open: the real exit pass still applies the hard stop.
3. `want` true for a symbol already in `real.open`: no buy.
4. `InsufficientFunds` with free ≥ min: sells `min(booked, free)`.
5. `InvalidOrder`: no retry loop; `exit_blocked` is set; one alert.
6. Fill with no `average`: exit price `null`, `exit_status: UNKNOWN`.
7. `check-books.py` still passes with `exit_pending` present.
8. The previous sell `cid` comes back FILLED: no new sell is sent, and the exit is recorded from that fill.
9. The `cid` lookup raises `NetworkError`: no sell is sent this run.

## Scope

One file (`scripts/trend_follower.py`) plus tests, in its own PR after the T0.3 implementation.
No crontab, `.env` or ledger changes.
