# T2.1 · Design: per-second tick ingest and recorder (paper only)

Status: design for T2.2. **Paper-only.** Market data only, from an endpoint that can't place orders.

## Goal

Stream per-second market data for the paper universe, keep it in memory for the live scanner (Phase 3),
and record it to disk so every strategy can be **replayed** on real ticks (T2.3, T4.3).

## Facts (measured or from the docs, 2026-09-26)

- Endpoint: `wss://data-stream.binance.vision`, the official **market-data-only** mirror. No user data, no
  orders ([ws docs](https://github.com/binance/binance-spot-api-docs/blob/master/web-socket-streams.md) l.50). It's the
  only Binance WS host reachable from dev (T1.2).
- Combined streams: `/stream?streams=a/b/c`; each message is `{"stream": "<name>", "data": <payload>}` (l.41-42).
- Limits (documented for `stream.binance.com`, assumed the same for the mirror): ≤1024 streams per connection, 5 incoming
  msgs/s per connection, 300 connects per 5 min per IP. The server pings every 20s and drops us after a minute with no pong. A
  connection lasts ≤24h (l.44-63).
- Payloads: `aggTrade` has event time `E` and trade time `T`; `kline_1s` has event time; **`bookTicker` has no
  timestamp**, only `u` (update id) (l.229-551). The recorder must stamp local receive time.
- **Measured load** (30s, 15 REAL_SYMS × {bookTicker, aggTrade, kline_1s}, one connection, 2026-09-25 ~17:12 UTC):
  bookTicker 482.7 msg/s at 146 B; aggTrade 42.9 msg/s at 202 B; kline_1s 14.9 msg/s at 337 B; **total 540 msg/s,
  82 KiB/s, about 6.75 GiB/day raw**. One sample at one hour; real load varies with volatility.
- Disk: D: has 81 GB free. `data/` is gitignored, so `data/local/` is too.

## Design

### Module layout (all new, under `src/trading/stream/`)
- `ws_client.py`: one combined-stream connection. aiohttp is already a dependency (no new deps). Answers pings
  (aiohttp does this with `autoping=True`). **Proactive reconnect at 23h** so the 24h cut never catches us mid-flow.
  Exponential backoff on failure (1s → 60s cap), with ≤300 connects per 5 min guaranteed by construction.
- `normalize.py`: turns each payload into a typed record:
  `Tick(kind, symbol, ts_exchange_ms | None, ts_recv_ns, fields…)`. `ts_exchange_ms` is `None` for bookTicker
  (never back-filled from `ts_recv`).
- `book.py`: in-memory **latest top-of-book and last trade** per symbol for the scanner. O(1) update; no history.
- `recorder.py`: append-only writer to `data/local/ticks/<YYYY-MM-DD>/<stream>/<HH>.jsonl`, rotated hourly and gzipped
  once closed. One line per record, UTC timestamps.
- `gaps.py`: gap detection. `aggTrade` ids (`a`) must be consecutive per symbol; a jump is a **recorded gap**
  (`{"kind":"gap","symbol":…,"from":a1,"to":a2}`). Reconnects are recorded as gap markers too. Gaps are data, never
  silently interpolated.
- `run_ingest.py` (CLI): `python -m trading.stream.run_ingest --symbols btc,eth,... --out data/local/ticks`.

### bookTicker volume
At ~480 msg/s, bookTicker is 89% of the bytes. The recorder keeps **every update whose best bid or ask *price* changes**,
plus **at least one snapshot per symbol per second**. Quantity-only updates in between are counted, not stored. Spread
and slippage analysis (T2.3, T4.1) needs price changes and the quantities at them, and both are kept. The share
dropped is **measured and reported** by T2.3 rather than assumed.

### Safety properties (tested in T2.2)
- The package imports no exchange client, no ccxt, nothing from `trading.exchange`. `tests/loop` blocks real-money
  modules, and T2.2 adds a test asserting the stream package's import graph stays clean.
- The host is pinned to `data-stream.binance.vision`. Changing it requires editing a constant, not passing a flag.
- There are no credentials anywhere in the path.

## Options considered

| Option | Why not |
|---|---|
| SQLite for raw ticks | 540 inserts/s is fine for SQLite, but row overhead and index growth cost more than gzip JSONL, and replay needs sequential reads only |
| Parquet | adds a dependency (pyarrow); worth it later only if replay speed becomes the bottleneck |
| REST polling | per-second REST across 15+ symbols burns request weight and loses intra-second events |
| Storing every bookTicker | ~6 GiB/day raw for one venue and 15 symbols; the quantity-only churn adds nothing the replay needs |

## Pre-mortem: it's 3 months later and this failed. Why?

- **Silent stall.** The socket stays open but data stops. Mitigation: a watchdog reconnects if no message arrives for 30s
  on a stream set whose normal rate is hundreds per second; the reconnect is recorded as a gap.
- **Clock skew makes latency stats wrong.** `ts_recv` uses `time.time_ns()`. Latency is only computed where an exchange
  timestamp exists (aggTrade/kline), and the skew isn't corrected. It's reported, not hidden.
- **Disk fills.** Retention: raw hourly files older than N days (default 14) are deleted by the recorder, and the size
  is logged each rotation.
- **Windows specifics.** Timer resolution and gzip-on-rotate file locks. T2.2 runs on Windows and is tested there.
- **The mirror disappears or is rate-limited differently.** The failure is loud (reconnect loop and alerts in the log);
  there's no automatic fallback to the trading hosts, by design.

## Test plan (T2.2)

1. `normalize` round-trips recorded fixture messages for each stream type (fixtures captured from the mirror).
2. The gap detector flags a missing `aggTrade` id range and a reconnect.
3. The bookTicker filter keeps price changes and one per second, and drops quantity-only updates; counts are exact.
4. Recorder rotation: an hour boundary closes and gzips the file; lines are valid JSON.
5. Import-graph test: `trading.stream` doesn't import `ccxt` or `trading.exchange`.
6. A live smoke test (`@pytest.mark.network`, opt-in): connect for 10s, receive ≥1 message per stream type.
